# 런던 자전거 대여 데이터 분석 작업로그

형식은 `01-washington/docs/claude_code_workflow.md`에서 설명한 방식을 따른다 —
"🔖 현재 진행 상태"는 매번 덮어써서 최신 상태만 유지하고, "작업 로그(시간순)"는
append-only로 이력을 보존한다. (참고: 이 파일은 세션 도중 실시간으로 갱신된 것이
아니라, 2026-08-19 세션 종료 시점에 대화 흐름을 되짚어 재구성했다 — 워싱턴처럼
작업 중 실시간으로 쓰지는 못했다는 점을 투명하게 남겨둔다.)

## 🔖 현재 진행 상태 (2026-08-19 기준)

- **완료**: 시간별(`london_merged.csv`) → 일별 변환, 연도별(2015/2016) 분리, STEP
  0~13 회귀분석 파이프라인 전체(전처리 확인 → VIF 재실측 → 5개 모델·8개 설정
  비교 → 최종 모델 채택 → 2016년 예측 → 잔차 분석), 이상치 탐지(보조 EDA),
  문서화(README/methodology/claude_code_workflow/변환 계획서 2종).
- **최종 채택 모델**: Ridge(α=10) — Test(2016) R²=0.7713, RMSE=4168.2, MAE=3171.8.
  워싱턴(XGBoost 우승)과 달리 선형 계열이 트리 계열을 앞선 결과.
- **원본 데이터**: `data/london_merged.csv`는 전 과정에서 읽기 전용으로만 사용,
  수정 없음.
- **남은 선택적 과제 (요청받지 않아 진행 안 함)**: `n_hours_recorded<24`인 날을
  제외한 버전으로 재학습해 성능 차이를 비교하는 실험, STEP12 회귀 가정 진단을
  더 정식으로(Breusch-Pagan 검정 등) 수행하는 것, `requirements.txt` 작성.
- **다음 세션에서 이어갈 것**: 특별히 없음 — 사용자가 다음에 요청하는 방향에 따름.

## 작업 로그 (시간순)

### 1. 데이터 최초 점검
`london_merged.csv`의 행/열/자료형/결측치/이상치/중복치를 정리. 17,414행 10컬럼,
결측 0, 완전 중복 0, IQR 이상치는 도메인상 정상 범위(폭염/강풍 등)로 판단.
시간 연속성 점검에서 이론상 17,544시간 중 130시간(0.74%) gap 발견.

### 2. 컬럼별 의미 분석
`cnt`(타깃), `t1`/`t2`(실측/체감기온), `hum`, `wind_speed`, `weather_code`(7종
코드), `is_holiday`, `is_weekend`, `season` 각각의 의미와 `cnt`와의 상관관계를
분석. 습도(-0.46)가 가장 강한 음의 상관, 기온(t1, +0.39)이 가장 강한 양의 상관.

### 3. 워싱턴-런던 컬럼 대조표
`hourly_to_daily_aggregation_rules.md`(워싱턴에서 작성된 문서) 기준으로 런던
컬럼을 3단 분류: 그대로 쓸 수 있는 규칙(연속형 평균, `cnt` 합계, carry-over
범주형) / 그대로 쓰면 안 되는 컬럼(`weather_code` — 코드 체계가 다르고 근사
규칙임) / 새로 만들어야 하는 컬럼(`dteday`/`yr`/`mnth`/`weekday`,
`casual`/`registered`는 복원 불가). **사용자가 "아직은 변환하지마"라고 명시**,
비교와 실행을 분리.

### 4. `weather_code` 처리 방안 확정
워싱턴 규칙(최빈값, 동률시 숫자 큰 코드 우선)을 런던에 그대로 쓸 수 있는지
검토. 웹 검색으로 런던 `weather_code`의 실제 정의(1=맑음 < ... < 26=눈)를 확인해
순서형임을 실측 검증. 다만 런던엔 대조용 일별 정답 파일이 없어 일치율 측정이
불가능하다는 한계를 발견. **사용자가 "기본 규칙 적용, 신뢰도 지표 컬럼은 만들지
마, 문서에 캐비앗만 남겨"로 결정** → `hourly_to_daily_aggregation_rules.md`에
캐비앗 절 추가.

### 5. 시간별→일별 변환 계획 및 실행
`london_hourly_to_daily_conversion_plan.md` 작성(파생 컬럼 정의, 결측 시간
처리 방침, 사전 점검 결과) → 승인 → `hourly_to_daily.py` 작성·실행. 결과: 730일,
`n_hours_recorded<24`인 날 34일, `cnt` 합계 무결성(시간별 총합=일별 총합) 검증
통과. 사용자가 "이 결과로 충분해"로 확정.

### 6. 연도별 분리
`split_daily_by_year.py`로 2015년(362일)/2016년(365일) 분리, 2017년 3일 제외.

### 7. 회귀분석 통합 계획
`01-washington` 폴더 전체(README/methodology/claude_code_workflow/src 10개
파일)를 검토·요약한 뒤 `london_regression_analysis_plan.md` 작성. Train=2015/
Test=2016 고정 분할, STEP0 스키마(안), 워싱턴과 다른 7가지 결정 사항(yr 상수화,
weekday/is_weekend/workingday 중복 예상, t1/t2 상관 0.99 실측, weather_code=26
희귀 범주 등)을 미리 문서화. 사용자 승인 후 실행 지시.

### 8. 파이프라인 구현 및 실행
`preprocessing.py`(STEP1 재확인) → `regression.py`(VIF 3라운드 실측으로
`season`/`is_weekend`/`workingday`/`t2` 제거 확정, OLS 적합) →
`random_forest.py`/`xgboost_model.py`(전체 적합 참고용) → `train_test_eval.py`
(OLS vs RF, 2015->2016) → `tune_linear.py`/`tune_random_forest.py`/
`tune_xgboost.py`(TimeSeriesSplit 그리드서치) 순으로 작성·실행. RF 내부 CV가
표본 부족(362일)으로 불안정(R²=-0.15)함을 발견.

### 9. 최종 모델 채택 및 예측
8개 모델/설정 비교 결과 Ridge(α=10, Test R²=0.7713)가 최고 성능. `predict_2016.py`
로 2016년 365일 예측 + 잔차 분석 — 24시간 미만 기록일의 평균 절대오차(4635.5)가
온전한 날(3104.7)보다 크다는 점을 실측 확인. 2016-12-25(크리스마스), 2016-06-24
(브렉시트 국민투표 결과 발표일, 9시간만 기록된 부분일)가 오차 최상위.

### 10. 보조 EDA 및 문서화
`anomaly_detection.py`/`plot_anomalies.py`로 730일 중 37일(5.1%) 이상치 탐지,
원인 1위는 날씨코드(43.2%). `README.md`(최종 리포트), `london_methodology.md`
(STEP0~13 적용 기록), `claude_code_workflow.md`(워싱턴과 다른 워크플로우 기록)
작성. 마지막으로 이 작업로그(`logs/`)를 워싱턴이 설명한 형식으로 재구성.
