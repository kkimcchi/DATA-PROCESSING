# Claude Code를 활용한 분석 워크플로우 (런던)

`01-washington/docs/claude_code_workflow.md`와 같은 목적의 기록이다 — "AI가 대신
분석해줬다"가 아니라, **분석을 이끄는 사람이 Claude Code를 어떻게 통제·검증하며
데이터 확인 → 변환 → 계획 → 모델링 → 문서화 전 과정을 끝까지 수행했는가**를
정리한다. 워싱턴과 같은 원칙을 공유하지만, 실제로 벌어진 방식은 꽤 달랐다 —
가장 큰 차이는 아래 1절에서 설명한다.

## 1. 문서 구조: 사전 지침 문서 대신 "단계마다 계획 문서 → 승인 → 실행"

워싱턴은 작업 시작 전에 README.md(방법론)와 CLAUDE.md(작업 규칙)를 먼저 써두고
시작했다고 설명돼 있다(다만 실제 `01-washington` 폴더에는 CLAUDE.md가 남아있지
않다 — 작업 중 썼지만 최종 배포 저장소에는 포함하지 않은 것으로 보인다). 런던은
처음엔 그런 사전 지침 문서 없이 시작했다 — 대신 **국면이 바뀔 때마다 계획 문서를
새로 쓰고, 사용자 승인을 받은 뒤에야 실행**하는 방식으로 진행됐다. `CLAUDE.md`는
프로젝트 후반부에 사용자가 별도로 요청해 이 시점까지 쌓인 규칙(원본 데이터 보존,
워싱턴 결론 재검증 원칙, 코딩 컨벤션 등)을 정리해 추가했다.

1. `hourly_to_daily_aggregation_rules.md`(원래 워싱턴에서 작성된 문서)를 근거로
   런던 컬럼을 대조하는 표를 먼저 요청받았다. 이때 사용자가 "**아직은 변환하지마**"
   라고 명시적으로 제동을 걸었다 — 비교 분석과 실제 변환 실행을 분리하라는 지시였다.
2. `weather_code` 처리 방법을 제안했을 때도 사용자는 세 가지 선택지 중 "기본 규칙
   적용 + 신뢰도 지표 컬럼은 만들지 마 + 문서에 캐비앗만 남겨"로 **부분 채택**했다 —
   AI가 제안한 것을 전부 받아들이지 않고 범위를 직접 골라낸 사례.
3. 실제 시간별→일별 변환도 `london_hourly_to_daily_conversion_plan.md`를 먼저 써서
   승인받은 뒤에야 `hourly_to_daily.py`를 작성·실행했다. 사용자는 "**우선은 여기까지만
   정리해줘**"라며 계획 단계와 실행 단계를 또 한 번 명확히 갈랐다.
4. 회귀분석도 마찬가지다 — `01-washington` 폴더 전체(README/methodology/
   claude_code_workflow/전체 src)를 먼저 검토해 요약하고, 그 결과를 바탕으로
   `london_regression_analysis_plan.md`를 작성해 승인받은 뒤에야 12개 스크립트를
   순서대로 작성·실행했다.

즉 런던 프로젝트는 "시작 전 지침 문서 한 벌"이 아니라 **"국면 전환마다 생기는 계획
문서 4벌"**(변환 규칙 대조 → 시간별→일별 변환 계획 → 회귀분석 통합 계획 →
methodology.md)로 의사결정 이력이 남는 구조가 됐다. 결과적으로 `docs/` 폴더 자체가
"무엇을, 왜, 어떤 순서로 결정했는가"의 타임라인 역할을 한다.

## 2. 단계별 확인 및 승인 절차

워싱턴처럼 "전체 파이프라인을 알아서 다 돌려줘"라고 맡기지 않았다. 매 요청이
이전 결과에 대한 확인 또는 다음 단계로의 명시적 지시였다.

- 데이터 요약(행/열/자료형/결측치/이상치/중복치) → 컬럼별 의미 분석 → 워싱턴·런던
  컬럼 대조표(3단 분류: 그대로 쓸 수 있음 / 쓰면 안 됨 / 새로 만들어야 함) →
  `weather_code` 처리 방법 제안 → 변환 계획서 → 변환 실행 → 연도별 분리 → 회귀
  통합 계획 → 실행, 순서로 **한 번에 하나씩** 요청이 이어졌다.
- 각 실행 단계 뒤에는 반드시 실측 결과(행 수, VIF 값, R² 등)를 출력해 보여주고 다음
  단계로 넘어갔다 — "24시간이 온전하지 않은 날이 몇일인지 알려줘" 같은 구체적
  검증 항목을 사용자가 미리 요구했고, 실행 후 정확히 그 숫자(34일 → Train/Test
  분리 후 18일/16일)를 보고했다.
- 이 대화에서는 별도의 `AskUserQuestion` 도구 호출 없이, 제안을 프롬프트 텍스트로
  제시하고 사용자의 다음 메시지로 승인/수정 지시를 받는 방식이 반복됐다(워싱턴
  사례의 "Random Forest 분석 범위를 먼저 질문" 같은 형식적 질문 도구 사용은 없었지만,
  같은 효과 — 진행 전 확인 — 를 텍스트 제안으로 달성했다).

## 3. 실측을 통한 검증 — "이전 프로젝트 결론을 그대로 베끼지 않는다"

워싱턴 문서의 핵심 교훈이 "짐작하지 말고 계산해서 확인하라"였는데, 런던에서도
같은 원칙이 여러 번 재현됐다 — 다만 매번 **워싱턴의 결론을 그대로 재사용하지 않고
런던 데이터에서 다시 실측**했다.

- **`weather_code` 코드 체계 검증**: 워싱턴의 `weathersit`(1~4)과 런던의
  `weather_code`({1,2,3,4,7,10,26})가 다른 체계라는 걸 확인한 뒤, "동률이면 숫자가
  큰 코드 우선"이라는 워싱턴 규칙을 그대로 쓸 수 있는지 판단하기 위해 실제 코드
  정의를 웹 검색으로 찾아 **순서형(맑음<구름조금<...<눈)임을 직접 확인**한 뒤에야
  규칙을 재사용하기로 결정했다. 동시에 "런던엔 대조용 일별 정답 파일이 없어 일치율
  자체를 측정할 수 없다"는, 워싱턴엔 없던 새로운 한계를 발견해 문서에 캐비앗으로
  남겼다.
- **VIF 다중공선성 재실측**: 워싱턴 결론(`workingday`/`atemp` 제거)을 그대로
  런던 `DROP_COLS`에 복사하지 않고, 런던 Train(2015) 데이터로 VIF를 처음부터
  다시 계산했다. 그 결과 워싱턴에는 없던 새로운 문제(`season`이 `mnth`로 100%
  결정됨 — 크로스탭으로 실측 확인)를 발견해 추가로 제거했다. 워싱턴과 겹치는
  패턴(파생 이진변수 조합, 온도쌍 중복)도 있었지만 "같은 이름의 컬럼이니 같은
  결론일 것"이라고 가정하지 않고 매번 다시 계산했다.
- **모델 순위 재검증**: 워싱턴에서 최종 우승 모델이 튜닝 XGBoost였다고 해서 런던도
  그럴 것이라 가정하지 않고 동일한 8개 설정을 처음부터 다시 학습·평가했다. 결과는
  정반대(런던은 Ridge가 1위)였고, 그 원인(Train 표본 크기 차이로 인한 트리 모델
  내부 CV 불안정, 실측 CV R²=-0.15)까지 실측으로 규명해 `methodology.md`에 남겼다.

## 4. 코드 재사용성을 통한 공정 비교 설계

워싱턴의 `build_design_matrix()`/`chronological_split()`/`evaluate()` 재사용
패턴을 런던에도 그대로 적용했다.

- `regression.py`의 `build_design_matrix()`(train+test를 합쳐서 인코딩한 뒤 분리 —
  `weather_code=26`이 Test에만 있는 문제를 구조적으로 해결)와 `load_train_test()`를
  `random_forest.py`, `xgboost_model.py`, `train_test_eval.py`, `tune_*.py`,
  `predict_2016.py`가 모두 import해서 재사용했다.
- `train_test_eval.py`의 `evaluate()`를 튜닝 스크립트 전체가 공유해, "R²/RMSE/MAE를
  어떻게 계산하는가"가 스크립트마다 미묘하게 달라지는 일을 막았다.
- 워싱턴과 달리 Train/Test가 파일 자체로 이미 분리돼 있어(`london_daily_2015.csv`
  / `_2016.csv`) `chronological_split()` 같은 분할 함수는 필요 없었고, 대신
  `load_train_test()`가 그 역할을 대신했다 — 데이터 구조가 다르면 재사용 패턴도
  기계적으로 복사하지 않고 구조에 맞게 바꿨다.

## 5. 세션 연속성: 계획 문서로 실시간 진행, 작업로그는 세션 종료 시점에 재구성

워싱턴은 `logs/{작업일자}_{데이터셋}_작업로그.md` 형식의 별도 작업로그를 **작업
중 실시간으로** 갱신하며 세션 연속성을 관리했다(다만 최종 배포 저장소에는 그
로그 파일 자체를 포함하지 않고, 재사용 가능한 산출물만 남겼다). 런던은 진행
과정에서는 실시간 로그 대신 1절에서 설명한 "국면마다 생기는 계획 문서"로 상태를
관리했다 — 각 계획 문서 자체가 "이 시점까지 뭘 결정했고 뭘 아직 안 했는지"를
담고 있어, 대화가 끊겨도 계획 문서만 다시 읽으면 진행 상태를 복원할 수 있는
구조였다.

세션이 마무리되는 시점에 사용자가 "logs 폴더도 워싱턴처럼 만들어줘"라고 요청해,
`logs/20260819_london_작업로그.md`를 워싱턴이 설명한 형식(🔖 현재 진행 상태 +
시간순 작업 로그)으로 **사후 재구성**했다. 이 로그는 워싱턴처럼 각 단계마다
실시간으로 쓴 것이 아니라, 대화 전체를 되짚어 한 번에 정리한 것이라는 차이를
로그 파일 자체에도 명시해뒀다 — "실시간 기록"과 "사후 재구성"은 신뢰도가 다르므로
구분해서 남기는 편이 낫다고 판단했다.

## 6. 환경 문제에 대한 실용적 대응

- **콘솔 인코딩 문제**: Windows 콘솔의 기본 코드페이지(cp949)가 한글 출력 스크립트의
  em dash(`—`) 문자를 인코딩하지 못해 `UnicodeEncodeError`가 발생했다(`regression.py`
  최초 실행 시). `PYTHONIOENCODING=utf-8` 환경변수를 붙여 실행하는 방식으로
  우회했다 — 워싱턴 사례(이미지 렌더링 문제, Bash 쓰기 권한 문제)와는 다른 종류의
  환경 제약이었다.

## 요약

런던 프로젝트에서 Claude Code는 워싱턴과 같은 원칙(실측 우선, 단계별 승인, 코드
재사용)을 따르되, **데이터셋과 대화 흐름이 다르면 그 원칙을 적용하는 방식도
다르게 조정**했다 — 사전 지침 문서 한 벌 대신 국면마다 계획 문서를 새로 쓰고,
워싱턴의 결론을 재사용하는 대신 매번 다시 실측하고, 파일이 이미 분리된 데이터
구조에 맞게 재사용 함수의 형태를 바꿨다. 특히 "이전 프로젝트에서 이미 검증된
결론이라도 새 데이터에서는 다시 확인한다"는 태도가 `weather_code` 순서성 검증,
VIF 재실측, 모델 순위 재검증 세 군데에서 반복적으로 나타났고, 그 결과 워싱턴과
정반대인 결론(트리 모델이 아니라 선형 모델이 우승)까지 놓치지 않고 잡아냈다.
