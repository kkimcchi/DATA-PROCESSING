# Claude Code를 활용한 분석 워크플로우

이 프로젝트는 Claude Code(CLI 기반 AI 코딩 에이전트)를 데이터 분석 파트너로 활용해
수행했습니다. 이 문서는 "AI가 대신 분석해줬다"는 이야기가 아니라, **분석을 이끄는 사람이
Claude Code를 어떻게 통제·검증하며 데이터 분석 워크플로우 전체(확인 → 정제 → 탐색 → 시각화
→ 모델링 → 해석 → 문서화)를 끝까지 수행했는가**를 정리한 기록입니다.

## 1. 프로젝트 지침 문서화 — CLAUDE.md / README.md

작업을 시작하기 전에 두 문서를 먼저 만들었습니다.

- **README.md**: STEP 0~13으로 구성된 범용 전처리·회귀분석 방법론 문서. "왜 이 단계가
  필요한가"를 코드보다 먼저 문서화해, 이후 모든 코드 작업이 즉흥적 시행착오가 아니라 근거
  있는 순서를 따르도록 설계했습니다.
- **CLAUDE.md**: Claude Code가 이 저장소에서 지켜야 할 작업 규칙(폴더 구조, 코딩 컨벤션,
  금지 사항, 작업로그 관리 방식)을 명시. "코드를 쓰기 전에 항상 README.md의 해당 STEP을 먼저
  읽는다"는 규칙을 못박아, 세션이 여러 번 끊기고 다시 시작되어도 같은 원칙을 지키도록 했습니다.

이 구조 덕분에 이후 대화에서 "다음 데이터셋도 같은 방식으로 분석해줘" 같은 요청이 가능해졌고,
실제로 이 방법론 문서는 `day.csv` 전용이 아닌 범용 파이프라인으로 재사용 가능하게
설계되었습니다(자세한 내용은 [methodology.md](methodology.md)).

## 2. 단계별 확인 및 승인 절차

Claude Code에게 "전체 파이프라인을 알아서 다 돌려줘"라고 맡기지 않고, 각 STEP마다 실행
결과(행/열 수, 결측치 개수, VIF 값, R² 등)를 출력시켜 검토한 뒤 다음 단계로 넘어가는 방식으로
진행했습니다. 예:

- STEP 3(이상치 처리)에서 `hum=0`(2011-03-10, 악천후인데 습도 0%로 기록된 물리적 모순)을
  발견했을 때, Claude Code가 바로 값을 고치지 않고 원인 추정(센서 결측 추정)과 처리 방법
  (결측 처리 후 선형 보간 vs 평균 대체)을 먼저 제시했고, 사용자가 방법을 확정한 뒤에야
  `preprocessing.py`에 반영했습니다.
- STEP 7(다중공선성)에서 `workingday`(VIF=inf)와 `atemp`(VIF≈650)를 발견했을 때도, 원인을
  설명(`workingday`가 `weekday`+`holiday`로 완전히 결정되는 파생변수임)한 뒤 사용자 승인을
  받고 제거했습니다.
- Random Forest를 처음 추가할 때는 "선형회귀와 동일 입력변수로 전체 데이터에 적합"과
  "바로 train/test 분할부터 적용" 중 분석 범위를 먼저 질문(AskUserQuestion)해 방향을
  정한 뒤 코드를 작성했습니다.

## 3. 사용자의 지적을 통한 방법론 교정

가장 중요한 지점은 **사용자가 Claude Code의 분석 설계를 검증하고 문제를 지적했을 때
실측으로 답했다**는 점입니다.

> "선형회귀만 하이퍼파라미터 튜닝을 안 하고 RF·XGBoost만 튜닝한 것 아니냐"

는 공정성 지적이 있었을 때, Claude Code는 "OLS는 정규방정식으로 유일해를 구하므로 튜닝할
하이퍼파라미터 자체가 없다"고 설명하는 데 그치지 않고, `alpha`라는 튜닝 가능한 하이퍼파라미터를
가진 **Ridge/Lasso**를 동일한 방법론(`TimeSeriesSplit` 그리드서치)으로 추가 실험해
`src/tune_linear.py`를 작성·실행했습니다. 결과적으로 "선형 계열은 튜닝 여부와 무관하게 성능이
비슷하다(Ridge≈OLS, Lasso는 더 나쁨)"는 것을 실측으로 확인해 공정성 우려를 근거로 해소했습니다.

또한 전체 데이터 적합 기준으로는 Random Forest(R²=0.98)가 선형회귀(R²=0.85)보다 훨씬 우수해
보였지만, Claude Code가 먼저 "이 비교만으로 RF가 우수하다고 결론 내리면 안 된다"는 과적합
경고를 제시했고, 이후 실제로 시간순 train/test 분할을 적용하자 순위가 완전히
뒤집혔습니다(선형회귀 test R²=0.65 > RF test R²=0.50). 이 경험을 바탕으로 "전체 데이터 적합
R²만으로 모델을 비교하지 말 것"이라는 규칙을 CLAUDE.md에 명문화해, 이후 XGBoost·튜닝 실험
전체에서 반드시 train/test 비교를 병행하도록 만들었습니다.

## 4. 코드 재사용성을 통한 공정 비교 설계

5개 모델(OLS, Ridge, Lasso, Random Forest, XGBoost)을 서로 다른 시점에 추가했지만, 모두
동일한 입력 변수·동일한 train/test 분할 기준으로 비교되도록 설계했습니다.

- `src/regression.py`의 `build_design_matrix()`(원-핫 인코딩·누수 변수 제거 로직)를
  `random_forest.py`, `train_test_eval.py`, `xgboost_model.py`, 튜닝 스크립트들이 모두
  import해 재사용
- `src/train_test_eval.py`의 `chronological_split()`/`evaluate()`를 이후 모든 모델·튜닝
  스크립트가 동일하게 재사용

새 모델을 추가할 때마다 이 함수들을 다시 구현하지 않고 재사용하도록 CLAUDE.md에 규칙으로
남겨, 모델 간 비교가 "우연히 비슷한 조건"이 아니라 "구조적으로 동일한 조건"이 되도록
보장했습니다.

## 5. 세션 연속성을 위한 작업로그 설계

대화가 길어지거나 세션이 끊기더라도 다음 세션(혹은 다음 사람)이 코드를 처음부터 다시
실행해보지 않고 진행 상황을 파악할 수 있도록, `logs/{작업일자}_{데이터셋}_작업로그.md`
형식의 작업로그를 매 작업 단위마다 갱신했습니다. 로그는 "🔖 현재 진행 상태"(매번
덮어써서 최신 상태만 유지) 섹션과 "작업 로그(시간순)"(append-only, 이력 보존) 섹션을
분리해, 빠른 재개와 전체 이력 추적을 동시에 만족하도록 설계했습니다. 이 저장소는 그
작업로그 중 재사용 가능한 산출물만 골라 정리한 결과물입니다.

## 6. 환경 문제에 대한 실용적 대응

작업 도중 두 가지 환경 제약이 발견되었고, Claude Code가 이를 우회하는 방식으로 작업 방식을
조정했습니다.

- 채팅 환경에서 Read 도구로 반환한 PNG 이미지가 렌더링되지 않는 문제를 발견 → 이후 모든
  차트를 채팅 인라인 표시 대신 `figures/` 폴더에 파일로 저장해 파일 탐색기/IDE에서 확인하는
  방식으로 전환
- 프로젝트 폴더에 대한 Bash 도구의 쓰기 권한 제약을 발견 → PowerShell 도구로 전환해 파일
  이동·복사 작업을 수행

## 요약

이 프로젝트에서 Claude Code는 "질문하면 답을 주는 도구"가 아니라, **사용자가 방법론(STEP
0~13)을 설계하고, 각 단계의 실행 결과를 직접 검토·승인하고, 실측 근거로 스스로의 설계를
검증(공정성 지적 → Ridge/Lasso 튜닝 실험, 전체 적합 R² 함정 → train/test 재평가)하며 CLI
환경에서 데이터 분석 워크플로우 전체를 주도적으로 수행**하기 위한 실행 환경으로 사용되었습니다.
